# Game Experience

Sudoku UI aims for the speed and clarity of leading browser Sudoku products without cloning their visual identity. The experience favors a calm editorial surface, direct controls, and equivalent keyboard and touch paths.

## Why This Experience Exists

A daily puzzle should reduce cognitive overhead outside the puzzle itself. Controls stay close to the board, state changes are immediate and legible, and recovery should make interruption safe rather than surprising. A persistent System/Light/Dark preference lets the experience fit the player's environment without changing gameplay.

## What the Experience Provides

The global header groups three compact pressed-state appearance choices with the account entry on every surface. Theme, difficulty, Notes, and Candidates use one shared selected-control language: a quiet accent-tinted surface, accent boundary, and accent ink adapted to each control scale. Selected state never borrows the solid emphasized-action fill, so a persistent preference cannot compete with the next task. In active play, Notes and Candidates form the named mode group while Erase, Undo, Redo, and Hint form a separate action group; desktop preserves the compact two-column rhythm, and narrow screens use a deliberate two-plus-four split so persistent modes do not read as interchangeable commands. The Sudoku brand always resolves to the configured application mount, so selecting it from the welcome surface cannot leave the product for an unrelated site that shares the host. Auto follows the operating-system color preference as it changes; explicit Light or Dark choices persist across refreshes and puzzles. Both palettes use the same semantic design tokens, visual hierarchy, non-color invalid cue, selected/focus treatment, and responsive geometry, including loading, dialog, paused, and completion surfaces. Healthy service state stays out of the header; only connection progress or a failure that blocks play is shown.

The welcome surface leads with one direct decision: “Choose your difficulty,” followed by “Pick a level, then start when you're ready” and one “Start [difficulty] puzzle” action. It carries no healthy idle sentence; the status surface appears only for actionable or temporary feedback. A secondary Sign in action remains available in the global header without blocking guest play. After sign-in, the same header position becomes an identity control that opens a responsive account sheet with the current profile, My games, and account settings without leaving the active board. Destructive game or account actions require explicit confirmation. A successful automatic claim announces “Game saved to your account” while preserving the active board. The selected level is a request preference; after creation, the active heading, status, completion, and refresh restoration display the API-owned actual difficulty even when fallback selected another grade. Familiar level buttons replace a select menu, and the browser remembers the latest level choice so refreshing the welcome surface does not unexpectedly return the player to Easy. Technical backend language stays out of the player-facing copy, and the same valid 9×9 puzzle used by the backend project communicates the product honestly rather than acting as decorative art. The preview needs no explanatory metadata: the board itself carries the product meaning. Small portrait phones omit the decorative preview so the complete decision flow stays immediate and the page never suggests that a cropped board is playable; portrait tablets and wider screens retain the full preview when it has enough space to communicate the product. The playable experience provides API-backed number and note entry, erase, undo/redo, applied hints, invalid-value feedback, an informational mistake count, and solved-state messaging. The count increases only after the API confirms an invalid value entry, never for notes or hints, and Undo, Redo, or erase cannot reduce it. It remains with the active game across refresh and recovery, while every newly created puzzle starts at zero; there is no strike limit or game-over consequence. Value entry appears immediately with a quiet checking treatment, then becomes normal or invalid as soon as its ordered backend response arrives; the browser never guesses Sudoku validity. Rapid value and note actions remain available and execute sequentially against each newly confirmed revision, preserving one backend action and one history position per intent. Undo and Redo are intentionally different: the first activation locks both history controls synchronously, keeps the confirmed board visible, and announces “Undoing…” or “Redoing…” until the authoritative response settles. Additional pointer, touch, or keyboard history activations during that transition do nothing, while ordinary input retains its immediate presentation path. The returned snapshot restores history availability; a failed history request keeps the confirmed board, unlocks both controls, and exposes the existing retry path. A conflict or failure removes unconfirmed projections so stale responses cannot conceal or overwrite confirmed results. Re-entering the value already present in a selected cell is a local no-op rather than a redundant API mutation, while note entry keeps its toggle behavior in the interface. Rapid note taps update the candidate grid immediately and debounce into complete-set API mutations, so one transport contract handles empty, single, and multiple notes without making network latency part of input feedback. A Notes mode or board selection change takes effect synchronously for the next input, including a digit entered before React has rendered the updated control state. Desktop mouse and pen selection commits when the pointer is pressed, so an authoritative board redraw cannot strand focus on the previous cell before the click completes; keyboard focus and touch click behavior remain unchanged. Mouse-to-keyboard entry therefore targets each newly chosen cell even when the previously selected cell contains an invalid value or its response settles during the next press. The experience defines one semantic number-pad activation independent of device. A thin input adapter maps mouse and keyboard to canonical click activation, while touch and pen commit on release and suppress the first click in the short post-touch window even when a mobile browser omits identifying pointer or compatibility-click fields. Device-specific event handling therefore cannot own or alter note, candidate, value, revision, or history behavior, and individual or rapid taps are neither delayed nor duplicated. Candidates and Notes are independent controls over one API-authoritative set per cell. Candidates on reveals every editable cell without mutation; Candidates off hides every cell without mutation. Notes changes digit input from value placement to candidate editing. Editing a hidden cell reveals only that cell and starts from an empty visible baseline, so stored `123` becomes visible `4` and then `45`; editing a visible `123` starts from that set and produces `1234` and then `12345`. The browser persists only the visibility mask by game identity, outside gameplay history. There is no parallel note map, candidate adoption, or source switch, and every new or restarted puzzle starts with Notes and Candidates off. Rapid candidate edits update one cell-local draft and debounce into complete `set-candidates` replacements; edits received while a request is in flight remain visible and serialize behind it, so an older response never rolls back newer input. Notes mode changes the number pad to a muted visual treatment and gives each key a note-specific accessible name, so the current input mode is clear beyond the separate toggle. Candidate digits and committed values scale from the rendered board container rather than the browser width, so both stay inside their fixed cell geometry when a window is dragged through short, wide, narrow, and breakpoint-adjacent sizes; the fixed 3×3 candidate grid always retains three visible rows. Available number-pad digits remain enabled before the player selects a cell so the pad communicates which digits remain; pressing one without a selection gives a direct prompt instead of mutating an arbitrary cell. Selecting a given disables the entire pad because the cell is immutable. In Notes mode, selecting any non-empty cell also disables the pad because notes can only belong to empty editable cells. Keyboard digits follow the same guards, so these invalid local states never send API actions. Erase is likewise available only when the selected editable cell has content that the current value or Notes mode can remove. A number-pad digit becomes unavailable after all nine non-invalid instances appear in the authoritative snapshot, and the same guard applies to keyboard input. Repeated invalid entries never consume that digit or block a later valid entry. The puzzle is the dominant visual object. Active play uses one compact difficulty heading instead of repeating the difficulty and a generic puzzle title; elapsed time, mistakes, Pause, and Start over share one restrained utility row. The grid sits directly on the game canvas without a decorative card, outer border, or shadow, leaving its own 3×3 boundaries as the visual frame. The number pad and tools sit in an unframed adjacent instrument panel on desktop and move beneath the board on narrow screens, so neither board nor control card chrome competes with the puzzle. Tool controls use one consistent outline-icon language: a pencil for note input, a 3×3 dot grid for candidate visibility, an eraser for clearing, directional history arrows, and a lightbulb for hints. These familiar task metaphors avoid arbitrary letters and decorative symbols. Text labels remain visible when the control surface has room; phone-sized controls become icon-only before labels can wrap or overflow, while explicit accessible names preserve the full action and toggle state. When height constrains the board below its desktop maximum, it stays centered in the full layout track to the left of the controls rather than drifting toward the number pad. On short wide screens, the smaller board aligns with the top of the taller controls instead of sinking below the visible game area. When the viewport has enough room, the game shell and board contract to fit without unnecessary vertical scrolling. Short phone viewports preserve board and control size by compressing outer game padding before allowing overflow, including the 412×839 Pixel 7 browser boundary. Genuinely constrained or display-scaled short viewports let the document grow and keep the footer after the complete board and controls instead of overlapping them. The responsive board uses explicit zero-minimum row and column tracks so values, notes, focus, and validation feedback cannot resize cells.

The Hint control opens a complete API-authored plan without changing the puzzle. A successful request turns Candidates on before the first step and leaves the authoritative grid visible after close or apply; typed hint facts then add step-specific teaching marks over that same grid. Wrong values and inconsistent candidate cells produce correction plans before any Sudoku strategy. Candidate corrections point to the exact cell, may mark locally impossible extras, and show the complete set allowed by accepted row, column, and box values without identifying the solved digit. Correction plans use a fix title without strategy metadata. Once validation passes, the surface keeps the strategy name and public grade fixed and presents one bounded reasoning step at a time. Every step for all 23 strategies uses the closed narration IR, and every conclusion identifies its exact digit and cell target; specialized placement and chain narration names additional highlighted objects directly instead of making the player count rows and columns. Each reference keeps a small `rNcN` locator for verification, while assistive technology receives the complete row, column, candidate, and unit wording. The browser renders a narration stream only when every discriminated token and target is valid, otherwise it displays the complete API-authored fallback message. Localization remains a later required backend-message-catalog evolution so translators can reorder typed targets and digits without moving Sudoku reasoning into React. Subset, intersection, fish, wing, BUG+1, and Unique Rectangle plans expose their exact typed facts and relationships before vocabulary. XY-Wing starts with one pivot-to-wing implication arrow, reveals both alternatives, and preserves both arrows on the result step. W-Wing draws its one solid conjugate-pair link throughout the explanation. Simple Coloring draws stable candidate nodes with visibly continuous solid rings centered on and fully enclosing each candidate digit, clear non-overlapping A/B labels, and solid strong links; X-Cycles numbers its nodes and alternates solid strong links with dashed weak links; XY-Chain numbers its nodes and draws directional implication arrows. Directional arrowheads use bounded board coordinates rather than stroke-relative SVG marker sizing, so mobile Safari cannot expand an arrowhead across the board or page. A compact persistent legend names every line, label, and number treatment. Each complex scene begins with one relation, expands to the complete graph, and preserves that graph while isolating the result; unit scope appears only when the unit itself is the current fact, so chain hints no longer wash most of the board with cell highlights. The surface never leads with the compact fallback summary. Typed cells, units, and candidates use role-specific shapes or lines plus matching accessible descriptions; color is supplemental. Back and Next navigate entirely in the browser, so learning does not create history entries or network mutations. `H` opens a hint, Left and Right move between steps, Enter applies only on the final step, and Escape closes; the same visible Back, Next, Apply hint, and Close controls remain the touch path. While the plan is open, its panel replaces the number pad, tools, and shortcut disclosure instead of stacking above disabled controls, so opening a hint cannot shift the board or push the footer under the control column. The visible board is read-only, including pointer selection. The final step offers Apply hint, which sends the exact previewed plan identity as one ordinary action; Close leaves the puzzle unchanged, and a successful apply is one Undo step. Applying a correction or elimination returns the updated authoritative candidate grid and remains one Undo step. A stale plan is replaced with a fresh preview for the authoritative revision, while a replacement with the same identity closes the teaching surface instead of trapping Apply in a refresh loop.

Pause conceals the puzzle and stops its elapsed-time display without changing authoritative gameplay state. The timer also stops while the page is hidden and resumes when the page becomes visible, without changing the player's explicit pause choice. API mutations disable conflicting controls but never suspend elapsed time; rapid hints and moves therefore cannot reduce the displayed duration. The active session pointer and timer presentation state survive refresh, while the board is always restored from the API. Initial session recovery uses a neutral loading state so the welcome surface never flashes before an active board is restored. Failed starts, moves, and restoration attempts retain the last confirmed state and offer a named retry action; revision conflicts reload the latest authoritative board. Solved games stop the timer and replace mutation controls with a completion panel that preserves the final elapsed time and offers direct paths to another board at the same level or back to level selection. Focus moves from the disappearing board cell to the completion heading, where a visible cue and the solved time make the state transition immediate for keyboard and assistive-technology users.

Leaving an unfinished game through the site logo or choosing Start over requires explicit confirmation. The current timer stops while either decision is open, Escape or the safe first action returns to the unchanged board, and only the named confirmation clears the browser's active-session pointer. The home action returns to the welcome surface without creating a session, then compares the running module entry with a no-cache copy of the deployed shell; if a newer asset is available, it reloads at that safe boundary instead of rendering an obsolete welcome surface. A failed check leaves normal navigation intact. The Start over decision gives Cancel safe initial focus and presents two equal choice surfaces: Replay this puzzle keeps the givens and resets the attempt, while Play a different puzzle owns its level picker and new-board action. Neither path uses accent fill to imply a recommendation. Replay waits for the authoritative restart before closing any open hint, zeroing elapsed time, clearing attempt-specific browser modes, focusing the fresh board, and showing one brief non-layout-shifting notice. Starting a different puzzle likewise discards the prior puzzle’s hint when the new board succeeds, so no explanation or marks can survive onto cleared or replaced state. A completed puzzle uses the same peer hierarchy for replay and another puzzle, while Choose another level remains quiet navigation because no unfinished progress remains to protect.

Creating a puzzle from the welcome surface keeps the level choice visible and changes the primary action to an inline preparing state because the player has not entered a game yet. Creating a replacement from the game surface instead conceals the stale board and controls behind a dedicated, named loading state as soon as the player confirms. The distinction preserves context on the welcome surface while preventing an old puzzle from appearing frozen or interactive during a slower replacement request. If replacement fails, the last confirmed board returns with its retry path intact.

Gameplay feedback follows a calm taxonomy. Successful value and candidate edits, restoration, hint close/application, and ordinary Undo/Redo completion remain visually silent; assistive technology still receives concise live announcements. Active state appears on the responsible control, including Notes, Candidates, Undoing, and Redoing. Restart and account-save success use a brief floating notice that never changes board or control geometry. Errors, conflicts, and retryable failures alone occupy the persistent inline status surface, while hints, pause, loading, completion, and confirmations keep their dedicated modes. During healthy play no explanatory status sentence or empty status divider remains visible. Board feedback has a deliberate visual hierarchy: the selected cell uses the only strong filled state, its row/column/box peers use one quieter but observable surface, and matching values use a restrained circular halo behind the digit instead of another full-cell fill or a competing edge mark. Candidate notes equal to the selected value use the same halo, so visual matching includes both committed values and penciled possibilities. Empty selections produce no matching-value marks. Invalid values use red ink plus a fixed-position bar below the digit. The marker is independent of font glyph metrics, so narrow and wide digits receive the same complete cue without looking like browser spellcheck or a decorative corner ornament. Invalid grid cells also expose their state to assistive technology. Pointer, touch, and arrow-key navigation keep DOM focus and selection on the same cell, while the focus and selection borders share one visual treatment instead of leaving two competing boxes on the board. The board uses one roving keyboard tab stop instead of placing all 81 cells in the page tab order; entering the board selects that cell, arrow keys move within it, and one Tab leaves for the controls. Candidate notes are included in each cell's accessible name even though their visual mini-grid stays hidden from assistive technology. A new or restored game begins without a highlighted cell, and clicking outside the board clears the current highlight. Game keyboard controls remain available while the page is focused: the first arrow selects the first editable cell when no selection exists, and later arrows navigate normally. Standard platform shortcuts undo and redo authoritative history (`Ctrl`/`Cmd`+`Z`, `Ctrl`/`Cmd`+`Shift`+`Z`, plus `Ctrl`+`Y`). Each response restores the exact backend-owned history state; entering a new value or note after Undo discards the abandoned Redo branch. `P` pauses or resumes without changing game state. A native, keyboard-accessible disclosure beside the controls documents the complete shortcut set, including hint controls, without permanently occupying limited mobile space. The gameplay board uses square corners so its rectangular selection cue never conflicts with outer corner curvature; the surrounding stage may stay softly rounded without changing grid geometry. The 3×3 boundaries remain visually dominant, and the mobile layout keeps every primary action reachable without precision pointing.

## Accessibility Constraints

Keyboard navigation and visible focus are first-class interaction paths. Motion honors reduced-motion preferences, controls expose names and state to assistive technology, and status changes use appropriate live semantics without stealing focus.
