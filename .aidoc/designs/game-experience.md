# Game Experience

Sudoku UI aims for the speed and clarity of leading browser Sudoku products without cloning their visual identity. The experience favors a calm editorial surface, direct controls, and equivalent keyboard and touch paths.

## Why This Experience Exists

A daily puzzle should reduce cognitive overhead outside the puzzle itself. Controls stay close to the board, state changes are immediate and legible, and recovery should make interruption safe rather than surprising. A persistent System/Light/Dark preference lets the experience fit the player's environment without changing gameplay.

## What the Experience Provides

The header exposes one compact native Theme control on every surface. System follows the operating-system color preference as it changes; explicit Light or Dark choices persist across refreshes and puzzles. Both palettes use the same semantic design tokens, visual hierarchy, non-color invalid cue, selected/focus treatment, and responsive geometry, including loading, dialog, paused, and completion surfaces.

The welcome surface leads with one decision—difficulty—and one primary action. The selected level is a request preference; after creation, the active heading, status, completion, and refresh restoration display the API-owned actual difficulty even when fallback selected another grade. Familiar level buttons replace a select menu, and the browser remembers the latest level choice so refreshing the welcome surface does not unexpectedly return the player to Easy. Technical backend language stays out of the player-facing copy, and the same valid 9×9 puzzle used by the backend project communicates the product honestly rather than acting as decorative art. The preview needs no explanatory metadata: the board itself carries the product meaning. Small portrait phones omit the decorative preview so the complete decision flow stays immediate and the page never suggests that a cropped board is playable; portrait tablets and wider screens retain the full preview when it has enough space to communicate the product. The playable experience provides API-backed number and note entry, erase, undo/redo, applied hints, invalid-value feedback, an informational mistake count, and solved-state messaging. The count increases only after the API confirms an invalid value entry, never for notes or hints, and Undo, Redo, or erase cannot reduce it. It remains with the active game across refresh and recovery, while every newly created puzzle starts at zero; there is no strike limit or game-over consequence. Value entry appears immediately with a quiet checking treatment, then becomes normal or invalid as soon as its ordered backend response arrives; the browser never guesses Sudoku validity. Rapid actions remain available and execute sequentially against each newly confirmed revision, preserving one backend action and one history position per intent. A conflict or failure removes unconfirmed projections so stale responses cannot conceal or overwrite confirmed results. Re-entering the value already present in a selected cell is a local no-op rather than a redundant API mutation, while note entry keeps its toggle behavior in the interface. Rapid note taps update the candidate grid immediately and debounce into complete-set API mutations, so one transport contract handles empty, single, and multiple notes without making network latency part of input feedback. A Notes mode or board selection change takes effect synchronously for the next input, including a digit entered before React has rendered the updated control state. Desktop mouse and pen selection commits when the pointer is pressed, so an authoritative board redraw cannot strand focus on the previous cell before the click completes; keyboard focus and touch click behavior remain unchanged. Mouse-to-keyboard entry therefore targets each newly chosen cell even when the previously selected cell contains an invalid value or its response settles during the next press. The experience defines one semantic number-pad activation independent of device. A thin input adapter maps mouse and keyboard to canonical click activation, while touch and pen commit on release and suppress the first click in the short post-touch window even when a mobile browser omits identifying pointer or compatibility-click fields. Device-specific event handling therefore cannot own or alter note, candidate, value, revision, or history behavior, and individual or rapid taps are neither delayed nor duplicated. An opt-in Candidates control, mirrored by the A key, reveals API-supplied candidates in a quieter style and remembers the setting only for the active puzzle across refreshes. Candidate preview hides saved manual notes without deleting them, and turning Candidates off restores those notes. Every newly created puzzle starts with Candidates and Notes off, no selected cell, an unpaused zeroed timer, and other browser-only controls at their defaults; API-authoritative history availability still comes from the new session snapshot. When Notes and Candidates are both active, the first digit edit sends one backend adoption action that replaces the complete manual-note map with current legal candidates and applies the requested toggle. The browser immediately presents the API-supplied candidate grid as editable note drafts and turns candidate preview off, so every later rapid toggle updates the same visible set while adoption is pending instead of starting another adoption. Successful adoption keeps Notes on, preserves any newer draft for one following complete-set save, and confirms the transition with the compact status “Candidates copied. Notes on.” without a confirmation dialog because one Undo restores the complete previous note map. Failed adoption discards the dependent drafts and restores candidate preview. During ordinary note editing, both additions and removals received after a request starts remain visible and wait behind the in-flight request before saving the latest complete set; an older response never rolls back what the player just entered. Notes mode changes the number pad to a muted visual treatment and gives each key a note-specific accessible name, so the current input mode is clear beyond the separate toggle. Candidate digits and committed values scale from the rendered board container rather than the browser width, so both stay inside their fixed cell geometry when a window is dragged through short, wide, narrow, and breakpoint-adjacent sizes; the fixed 3×3 candidate grid always retains three visible rows. Available number-pad digits remain enabled before the player selects a cell so the pad communicates which digits remain; pressing one without a selection gives a direct prompt instead of mutating an arbitrary cell. Selecting a given disables the entire pad because the cell is immutable. In Notes mode, selecting any non-empty cell also disables the pad because notes can only belong to empty editable cells. Keyboard digits follow the same guards, so these invalid local states never send API actions. Erase is likewise available only when the selected editable cell has content that the current value or Notes mode can remove. A number-pad digit becomes unavailable after all nine non-invalid instances appear in the authoritative snapshot, and the same guard applies to keyboard input. Repeated invalid entries never consume that digit or block a later valid entry. The puzzle is the dominant visual object; status and tools sit in one quiet adjacent control surface on desktop and move beneath the board on narrow screens. Tool controls use one consistent outline-icon language: a pencil for notes, a 3×3 dot grid for candidates, an eraser for clearing, directional history arrows, and a lightbulb for hints. These familiar task metaphors avoid arbitrary letters and decorative symbols. Text labels remain visible when the control surface has room; phone-sized controls become icon-only before labels can wrap or overflow, while explicit accessible names preserve the full action and toggle state. When height constrains the board below its desktop maximum, it stays centered in the full layout track to the left of the controls rather than drifting toward the number pad. On short wide screens, the smaller board aligns with the top of the taller controls instead of sinking below the visible game area. When the viewport has enough room, the game shell and board contract to fit without unnecessary vertical scrolling. Short phone viewports preserve board and control size by compressing outer game padding before allowing overflow, including the 412×839 Pixel 7 browser boundary. Genuinely constrained or display-scaled short viewports let the document grow and keep the footer after the complete board and controls instead of overlapping them. The responsive board uses explicit zero-minimum row and column tracks so values, notes, focus, and validation feedback cannot resize cells.

Pause conceals the puzzle and stops its elapsed-time display without changing authoritative gameplay state. The timer also stops while the page is hidden and resumes when the page becomes visible, without changing the player's explicit pause choice. API mutations disable conflicting controls but never suspend elapsed time; rapid hints and moves therefore cannot reduce the displayed duration. The active session pointer and timer presentation state survive refresh, while the board is always restored from the API. Initial session recovery uses a neutral loading state so the welcome surface never flashes before an active board is restored. Failed starts, moves, and restoration attempts retain the last confirmed state and offer a named retry action; revision conflicts reload the latest authoritative board. Solved games stop the timer and replace mutation controls with a completion panel that preserves the final elapsed time and offers direct paths to another board at the same level or back to level selection. Focus moves from the disappearing board cell to the completion heading, where a visible cue and the solved time make the state transition immediate for keyboard and assistive-technology users.

Leaving an unfinished game through the site logo or starting another puzzle requires explicit confirmation. The current timer stops while either decision is open, Escape or the safe first action returns to the unchanged board, and only the named confirmation clears the browser's active-session pointer. The home action returns to the welcome surface without creating a session. The new-puzzle decision includes the full difficulty choice, so the player can change levels before the confirmed API session is created.

Creating a puzzle from the welcome surface keeps the level choice visible and changes the primary action to an inline preparing state because the player has not entered a game yet. Creating a replacement from the game surface instead conceals the stale board and controls behind a dedicated, named loading state as soon as the player confirms. The distinction preserves context on the welcome surface while preventing an old puzzle from appearing frozen or interactive during a slower replacement request. If replacement fails, the last confirmed board returns with its retry path intact.

Routine status feedback stays concise enough for one line on phone widths; persistent control state communicates the detail instead of explanatory prose that shifts the board and controls. Board feedback has a deliberate visual hierarchy: the selected cell uses the only strong filled state, its row/column/box peers use one quieter but observable surface, and matching values use a restrained circular halo behind the digit instead of another full-cell fill or a competing edge mark. Candidate notes equal to the selected value use the same halo, so visual matching includes both committed values and penciled possibilities. Empty selections produce no matching-value marks. Invalid values use red ink plus a fixed-position bar below the digit. The marker is independent of font glyph metrics, so narrow and wide digits receive the same complete cue without looking like browser spellcheck or a decorative corner ornament. Invalid grid cells also expose their state to assistive technology. Pointer, touch, and arrow-key navigation keep DOM focus and selection on the same cell, while the focus and selection borders share one visual treatment instead of leaving two competing boxes on the board. The board uses one roving keyboard tab stop instead of placing all 81 cells in the page tab order; entering the board selects that cell, arrow keys move within it, and one Tab leaves for the controls. Candidate notes are included in each cell's accessible name even though their visual mini-grid stays hidden from assistive technology. A new or restored game begins without a highlighted cell, and clicking outside the board clears the current highlight. Game keyboard controls remain available while the page is focused: the first arrow selects the first editable cell when no selection exists, and later arrows navigate normally. Standard platform shortcuts undo and redo authoritative history (`Ctrl`/`Cmd`+`Z`, `Ctrl`/`Cmd`+`Shift`+`Z`, plus `Ctrl`+`Y`), while `P` pauses or resumes without changing game state. A native, keyboard-accessible disclosure beside the controls documents the complete shortcut set without permanently occupying limited mobile space. The gameplay board uses square corners so its rectangular selection cue never conflicts with outer corner curvature; the surrounding stage may stay softly rounded without changing grid geometry. The 3×3 boundaries remain visually dominant, and the mobile layout keeps every primary action reachable without precision pointing.

## Accessibility Constraints

Keyboard navigation and visible focus are first-class interaction paths. Motion honors reduced-motion preferences, controls expose names and state to assistive technology, and status changes use appropriate live semantics without stealing focus.
