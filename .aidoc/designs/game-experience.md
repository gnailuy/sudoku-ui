# Game Experience

Sudoku UI aims for the speed and clarity of leading browser Sudoku products without cloning their visual identity. The experience favors a calm editorial surface, direct controls, and equivalent keyboard and touch paths.

## Why This Experience Exists

A daily puzzle should reduce cognitive overhead outside the puzzle itself. Controls stay close to the board, state changes are immediate and legible, and recovery should make interruption safe rather than surprising. A persistent System/Light/Dark preference lets the experience fit the player's environment without changing gameplay.

## What the Experience Provides

The global header groups a compact language selector, three pressed-state appearance choices, and the account entry on every surface. Their outer controls share one consistent height at desktop and phone widths, so the language preference does not sit above or below its neighboring global controls. The selector keeps complete language names in its native menu, ordered predictably after Auto, while using an approved compact name when needed, including Português for Português (Brasil). Its closed label and chevron form one centered unit inside a restrained fixed width, so the indicator cannot make the label look displaced or leave a one-sided void; every production language remains complete rather than clipped. It labels its automatic choice Auto while the appearance control uses System, dismisses pointer focus after a selection, and retains visible keyboard focus. At phone widths, the sign-in action uses a compact person icon with its complete accessible name so the wider selector does not force the header beyond the viewport. Auto follows the first recognized browser language, including primary English before any later installed language pack; explicit English, Simplified Chinese, Traditional Chinese, Dutch, Brazilian Portuguese, Spanish, Japanese, Korean, Polish, French, German, Russian, Arabic, Indonesian, Hindi, Italian, Thai, Turkish, Vietnamese, or Ukrainian choices persist globally. Switching language updates the current presentation in place while preserving the active game, elapsed time, selection and focus, modes, dialogs, and open hint step. Theme, difficulty, Notes, and Candidates use one shared selected-control language: a quiet accent-tinted surface, accent boundary, and accent ink adapted to each control scale. Selected state never borrows the solid emphasized-action fill, so a persistent preference cannot compete with the next task. In active play, Notes and Candidates form the named mode group while Erase, Undo, Redo, and Hint form a separate action group; desktop preserves the compact two-column rhythm, and narrow screens use a deliberate two-plus-four split so persistent modes do not read as interchangeable commands. The Sudoku brand always resolves to the configured application mount, so selecting it from the welcome surface cannot leave the product for an unrelated site that shares the host. System follows the operating-system color preference as it changes; explicit Light or Dark choices persist across refreshes and puzzles. Both palettes use the same semantic design tokens, visual hierarchy, non-color invalid cue, selected/focus treatment, and responsive geometry, including loading, dialog, paused, and completion surfaces. Healthy service state stays out of the header; only connection progress or a failure that blocks play is shown.

The welcome surface leads with one direct decision: “Choose your difficulty,” followed by “Pick a level, then start when you're ready” and one “Start [difficulty] puzzle” action. It carries no healthy idle sentence; the status surface appears only for actionable or temporary feedback. A secondary Sign in action remains available in the global header without blocking guest play. After sign-in, the same header position becomes an identity control that opens a responsive account sheet with the current profile, My games, and account settings without leaving the active board. Destructive game or account actions require explicit confirmation. Opening a saved game, deleting one or all games, signing out, revoking sessions, and deleting the account replace generic disabled controls with target-specific pending labels. A submitted destructive confirmation remains visible, locked, and named until the authoritative response succeeds; Escape and Cancel cannot hide an uncertain operation. Automatic claim replaces the board with a named “Saving your puzzle to your account…” transition while the ownership response is uncertain, states that the local copy remains safe, and admits exactly one request. A successful automatic claim announces “Game saved to your account” while preserving the active board. The selected level is a request preference; after creation, the active heading, status, completion, and refresh restoration display the API-owned actual difficulty even when fallback selected another grade. Familiar level buttons replace a select menu, and the browser remembers the latest level choice so refreshing the welcome surface does not unexpectedly return the player to Easy. Technical backend language stays out of the player-facing copy, and the same valid 9×9 puzzle used by the backend project communicates the product honestly rather than acting as decorative art. The preview needs no explanatory metadata: the board itself carries the product meaning. Small portrait phones omit the decorative preview so the complete decision flow stays immediate and the page never suggests that a cropped board is playable; portrait tablets and wider screens retain the full preview when it has enough space to communicate the product. The playable experience provides API-backed number and note entry, erase, undo/redo, applied hints, invalid-value feedback, an informational mistake count, and solved-state messaging. The count increases only after the API confirms an invalid value entry, never for notes or hints, and Undo, Redo, or erase cannot reduce it. It remains with the active game across refresh and recovery, while every newly created puzzle starts at zero; there is no strike limit or game-over consequence. Value entry appears immediately with a quiet checking treatment, then becomes normal or invalid as soon as its ordered backend response arrives; the browser never guesses Sudoku validity. Rapid value and note actions remain available and execute sequentially against each newly confirmed revision, preserving one backend action and one history position per intent. Undo and Redo are intentionally different: the first activation locks both history controls synchronously, keeps the confirmed board visible, and announces “Undoing…” or “Redoing…” until the authoritative response settles. Additional pointer, touch, or keyboard history activations during that transition do nothing, while ordinary input retains its immediate presentation path. The returned snapshot restores history availability; a failed history request keeps the confirmed board, unlocks both controls, and exposes the existing retry path. A conflict or failure removes unconfirmed projections so stale responses cannot conceal or overwrite confirmed results. Re-entering the value already present in a selected cell is a local no-op rather than a redundant API mutation, while note entry keeps its toggle behavior in the interface. Rapid note taps update the candidate grid immediately and debounce into complete-set API mutations, so one transport contract handles empty, single, and multiple notes without making network latency part of input feedback. A Notes mode or board selection change takes effect synchronously for the next input, including a digit entered before React has rendered the updated control state. Desktop mouse and pen selection commits when the pointer is pressed, so an authoritative board redraw cannot strand focus on the previous cell before the click completes; keyboard focus and touch click behavior remain unchanged. Mouse-to-keyboard entry therefore targets each newly chosen cell even when the previously selected cell contains an invalid value or its response settles during the next press. The experience defines one semantic number-pad activation independent of device. A thin input adapter maps mouse and keyboard to canonical click activation, while touch and pen commit on release and suppress the first click in the short post-touch window even when a mobile browser omits identifying pointer or compatibility-click fields. Device-specific event handling therefore cannot own or alter note, candidate, value, revision, or history behavior, and individual or rapid taps are neither delayed nor duplicated. Candidates and Notes are independent controls over one API-authoritative set per cell. Candidates on reveals every editable cell without mutation; Candidates off hides every cell without mutation. Notes changes digit input from value placement to candidate editing. Editing a hidden cell reveals only that cell and starts from an empty visible baseline, so stored `123` becomes visible `4` and then `45`; editing a visible `123` starts from that set and produces `1234` and then `12345`. The browser persists only the visibility mask by game identity, outside gameplay history. There is no parallel note map, candidate adoption, or source switch, and every new or restarted puzzle starts with Notes and Candidates off. Rapid candidate edits update one cell-local draft and use a trailing-edge debounce that restarts after every edit, so one uninterrupted physical input burst becomes one complete `set-candidates` replacement. Edits received while a request is in flight remain visible and serialize behind it, so an older response never rolls back newer input. Notes mode changes the number pad to a muted visual treatment and gives each key a note-specific accessible name, so the current input mode is clear beyond the separate toggle. Candidate digits and committed values scale from the rendered board container rather than the browser width, so both stay inside their fixed cell geometry when a window is dragged through short, wide, narrow, and breakpoint-adjacent sizes; the fixed 3×3 candidate grid always retains three visible rows. Available number-pad digits remain enabled before the player selects a cell so the pad communicates which digits remain; pressing one without a selection gives a direct prompt instead of mutating an arbitrary cell. Selecting a given disables the entire pad because the cell is immutable. In Notes mode, selecting any non-empty cell also disables the pad because notes can only belong to empty editable cells. Keyboard digits follow the same guards, so these invalid local states never send API actions. Erase is likewise available only when the selected editable cell has content that the current value or Notes mode can remove. A number-pad digit becomes unavailable after all nine non-invalid instances appear in the authoritative snapshot, and the same guard applies to keyboard input. Repeated invalid entries never consume that digit or block a later valid entry. The puzzle is the dominant visual object. Active play uses one compact difficulty heading instead of repeating the difficulty and a generic puzzle title; elapsed time, mistakes, Pause, and Start over share one restrained utility row. The grid sits directly on the game canvas without a decorative card, outer border, or shadow, leaving its own 3×3 boundaries as the visual frame. The number pad and tools sit in an unframed adjacent instrument panel on desktop and move beneath the board on narrow screens, so neither board nor control card chrome competes with the puzzle. Tool controls use one consistent outline-icon language: a pencil for note input, a 3×3 dot grid for candidate visibility, an eraser for clearing, directional history arrows, and a lightbulb for hints. These familiar task metaphors avoid arbitrary letters and decorative symbols. Text labels remain visible when the control surface has room; phone-sized controls become icon-only before labels can wrap or overflow, while explicit accessible names preserve the full action and toggle state. When height constrains the board below its desktop maximum, it stays centered in the full layout track to the left of the controls rather than drifting toward the number pad. On short wide screens, the smaller board aligns with the top of the taller controls instead of sinking below the visible game area. When the viewport has enough room, the game shell and board contract to fit without unnecessary vertical scrolling. Short phone viewports preserve board and control size by compressing outer game padding before allowing overflow, including the 412×839 Pixel 7 browser boundary. Genuinely constrained or display-scaled short viewports let the document grow and keep the footer after the complete board and controls instead of overlapping them. The responsive board uses explicit zero-minimum row and column tracks so values, notes, focus, and validation feedback cannot resize cells.

Unknown valid descriptors use bounded English fallback; malformed descriptors use a localized generic failure. Pause conceals the puzzle and stops its elapsed-time display without changing authoritative gameplay state. The timer also stops while the page is hidden and resumes when the page becomes visible, without changing the player's explicit pause choice. Duplicate activation cannot create a second request. The distinction preserves context on the welcome surface while preventing an old puzzle from appearing frozen or interactive during a slower replacement request. If replacement fails, the last confirmed board returns with its retry path intact.

During healthy play no explanatory status sentence or empty status divider remains visible. ## Accessibility Constraints

Keyboard navigation and visible focus are first-class interaction paths. Motion honors reduced-motion preferences, controls expose names and state to assistive technology, and status changes use appropriate live semantics without stealing focus.
